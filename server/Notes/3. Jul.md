1. NEVER TRUST CLIENT-SUPPLIED URLs FOR SERVER-SIDE FETCHES (SSRF + Cost Abuse)
   When a server fetches a URL on behalf of a client request, that URL must
   come from a server-controlled registry — never from req.body. Two real
   attack vectors exist if you do:
   - Cost abuse: a malicious user sends a huge image URL, your vendor
     (BFL) fetches and processes it at full megapixel cost, your billing
     account gets charged. At scale this is a targeted billing attack.
   - SSRF (Server-Side Request Forgery): if your code ever fetches the URL
     itself before forwarding it, an attacker sends an internal URL
     (e.g. http://169.254.169.254/latest/meta-data/ on AWS) and your server
     leaks internal infrastructure metadata.
   Fix pattern: client sends productSku (what), server resolves the actual
   URL from a trusted internal registry (which). Same principle applies to
   file paths, S3 keys, internal service endpoints — anything the server
   acts on that could be abused if the client controlled the value directly.
 
2. ASYNC VENDOR APIs REQUIRE A DIFFERENT INTEGRATION SHAPE THAN BLOCKING CALLS
   Your existing HF calls (hf.textToImage, inference.imageToImage) are
   single-await blocking calls — submit and get the result back in one
   round-trip. BFL's API is fundamentally different:
   - Submit request -> get back a requestId and a pollingUrl
   - Poll pollingUrl every N seconds until status === 'Ready'
   - Fetch the result from a delivery URL — which expires in 10 minutes
   This async submit/poll/download lifecycle is the standard pattern for
   most serious AI vendor APIs (Replicate, Runway, ElevenLabs, etc.) and
   maps directly onto your BullMQ worker architecture: the worker is the
   right place to run a polling loop since it's already a background process
   with no HTTP response timeout to worry about. Learning: know the
   difference between synchronous (blocking) and asynchronous (polling)
   vendor API patterns before you integrate — the integration shape,
   error handling, and timeout strategy are completely different.
 
3. ONE REGISTRY, TWO STRATEGIES — CONFIGURATION AS A SINGLE SOURCE OF TRUTH
   Both compositing strategies (sharp-based Option A and BFL multi-ref
   Option B) now read from the same WRAPPER_OVERLAY_REGIONS registry in
   imageCompositeService.js — Option A reads templatePath, Option B reads
   publicUrl. This is a real architectural pattern: when two different code
   paths need to act on the same domain entity (a product wrapper), keep
   that entity's configuration in one place and let each strategy read the
   field it needs. The alternative — two separate config objects in two
   separate files for the same SKUs — would mean every time you add a new
   wrapper product you'd have to update two places, and they'd inevitably
   drift. Centralizing also means the pre-check (hasRegionConfig) works
   identically for both job types without duplicating the validation logic.
